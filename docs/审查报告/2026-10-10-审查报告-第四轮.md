## 二、缺陷：一次性抉择卡可被重复结算 🔴

### 2.1 现象

抉择卡的设计约定写在代码注释里：

> `engine.lua:147` — 抉择卡：`choiceUsed` 整局一次性，选择后不再发

**实测：落定后该卡仍会被重新发牌，并可再次落定。5 个剧本全部复现。**

```
lisi      ACT-65      落定后仍被重新发牌 = true   第 2 次落定 = 执行
jingke    JK-ACT-57   落定后仍被重新发牌 = true   第 2 次落定 = 执行
hanxin    HX-ACT-65   落定后仍被重新发牌 = true   第 2 次落定 = 执行
xiangyu   XY-ACT-65   落定后仍被重新发牌 = true   第 2 次落定 = 执行
chensheng CS-ACT-65   落定后仍被重新发牌 = true   第 2 次落定 = 执行
```

更直接的度量：**把 12 张抉择卡全部标记为已用后，40 轮发牌中仍出现 19 次**。

### 2.2 根因

`scripts/qingshi/engine.lua` `beginRounds()`（约 570–587 行）：

```lua
local crest = {}
for i = 1, #pool do
  local a = pool[i]
  if J(a.choice) and not self.choiceUsed[a.id] then crest[#crest + 1] = a end   -- ← 只过滤 crest
end
local cpick = nil
if #crest > 0 and self.choiceGap >= 2 then
  cpick = crest[math.floor(deal() * #crest) + 1]
  self.choiceGap = 0
  for i = 1, #pool do
    if pool[i] == cpick then table.remove(pool, i) break end     -- ← 只移除「被强制选中」的那张
  end
end
local n = math.min(3, #pool)
for k = 1, n do
  local idx = math.floor(deal() * #pool) + 1
  picks[#picks + 1] = table.remove(pool, idx)                     -- ← pool 里仍有已用过的抉择卡
end
```

`choiceUsed` 只用于构造**强制发牌候选** `crest`，**从未用于剔除普通抽卡池 `pool`**。于是：

1. 已落定的抉择卡仍留在 `pool` 中
2. 它会被随后的 3 张常规抽牌选中
3. 打出后再次进入 `choice` 阶段，再次落定、再次结算 `opt.eff`

`prot/engine.js` 的实现**完全相同**（`crest` 用 `pool.filter(...)`，`pool` 未过滤）。

### 2.3 为什么 100/100 对拍没抓到

因为 **JS 与 Lua 有完全相同的缺陷**，两侧行为一致，逐位对拍必然全绿。

> 这是差分测试的固有盲区：**对拍能证明「两侧一致」，不能证明「两侧都对」**。这类语义缺陷必须靠独立审查发现——也正是本轮的主要价值。

### 2.4 影响

- 一次性卡变成可重复刷新的卡，玩家可选收益最高的那条选项反复结算
- `ACTION_RULES.diminish` 对抉择卡**不生效**（`chooseCardOption` 里 `noDim` 分支取 `deepCopy(opt.eff)`），故重复结算每次都是**全额收益**，无递减惩罚
- 受影响的选项若含 `dev`/`hist`/`merit`/`ach`，还能刷偏离度、史评、功勋与成就

实测收益幅度取决于玩家选哪条选项（我的度量仅统计 `quanshi+caifu+shengwang` 三项，hanxin/chensheng 上单次即 +2/+1）。

### 2.5 建议修复

在构造 `crest` **之前**先从 `pool` 剔除已用过的抉择卡：

```lua
-- 已落定的抉择卡整局不再发:必须先从 pool 剔除。
-- 仅过滤 crest(强制发牌候选)不够——它们仍会被下面的常规抽牌选中并重复落定。
local kept = {}
for i = 1, #pool do
  local a = pool[i]
  if not (J(a.choice) and self.choiceUsed[a.id]) then kept[#kept + 1] = a end
end
pool = kept
```

`crest` 的过滤随之可简化为 `if J(a.choice)`。

**改动须知**：
1. **JS 与 Lua 必须同步修改**，否则对拍立刻失败
2. 修改会改变 `deal()` 的消耗序列，**`golden.json` 必须重新生成**（用 `p1-golden.js`）
3. 重新生成基准后，**应逐局 diff 漂移范围**（参照第三轮附录 E 的做法：确认变化仅集中在受影响的剧本/字段），而不是直接采信

## 五、观察项（非缺陷）

1. **`choice.title` 全部未使用**：60 张抉择卡无一填写 `title`，引擎回落用 `a.name`（见 `getChoiceCard`）。不算缺陷，但若设计上有独立标题需补。
2. **抉择卡在回合页无视觉标识**：`renderRound` 对普通行动卡与抉择卡一视同仁，玩家需打出后才发现是抉择。可考虑加标记。
3. **`reConcentrate` 未使用字段**：见 `data` 中 `cuncun`（存续）已参与评分，无需处理。

## 六、结论

1. **必须修复**：抉择卡重复结算（第二节）。这是本轮唯一的真缺陷，且因两侧同错而对对拍网隐形。
2. **新功能其余部分质量良好**：状态机、存读档、索引契约、路由、数据规整度均经实测通过。
3. **流程建议**（连续三轮出现同一问题）：
   - 审查前冻结 HEAD，避免基线漂移导致结论过期
   - `golden.json` 重新生成时，**必须附逐局漂移 diff** 作为评审材料
   - 差分测试无法覆盖「两侧同错」的语义缺陷，建议为关键规则补充**不依赖 JS 的断言**（例如：抉择卡落定后 N 轮内不得再出现在 offer 中）

### F.6 顺带发现的健壮性缺口（未修，仅记录）

用旧 golden 回放时出现：

```
LUA-ERR: /engine.lua:722: attempt to perform arithmetic on a nil value (local 'i')
```

`Game:playCard(i)` 首行即 `self.offer[i + 1]`，**无 `i` 的 nil 守卫**；`i` 为 nil 时直接崩。

- **触发路径**：`p2-replay` 驱动在基准失配时读到异常步长，`tonumber(nil)` 得 nil
- **产品可达性**：**不可达**。UI 侧索引恒来自 `ipairs(offer)`，不会传 nil
- **建议**：补 `if type(i) ~= 'number' then return nil end`，属低成本加固

修复 golden 后该错误不再出现（属基准失配的产物，非产品缺陷）。
