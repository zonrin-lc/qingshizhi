#### P0-1　`and nil or` 三元陷阱：锁定选项实际可点击 🔴 ✅已修复

**位置**：`scripts/qingshi/ui/game.lua:338`、`game.lua:427`、`game.lua:497`、`scripts/qingshi/ui/theme.lua:290`

```lua
onClick = o.locked and nil or function() M.doChoose(i - 1) end
```

Lua 中 `x and nil or y` **恒等于 `y`**（`locked and nil` 得 `nil`，`nil or fn` 得 `fn`）。作者意图是「锁定则不给回调」，实际是**无论是否锁定都挂了 handler**。

实测确认：

```
locked_card_has_onClick=true  click_would_fire=1
```

**影响**：玩家点击灰显（`opacity=0.55`）的锁定选项会触发 `doChoose`，走进引擎后被 `choose()` 的 `entry.locked` 拦下返回 `nil`，最终弹出 `S.thawOpts`。**功能上「侥幸没崩」，但表现为点了没反应的死 UI**，且视觉暗示与实际可点性矛盾。`theme.Btn` 的 `disabled` 同理，禁用按钮依然可点。

**修复**：改用显式分支

```lua
local onClick = nil
if not o.locked then onClick = function() M.doChoose(i - 1) end end
```

> 注：`lua-apicheck` 已有「优先级陷阱」检查规则（`lua-apicheck.js:64`），但只覆盖 `X + (cond) and A or B` 一种形态，漏了 `and nil or` 这一类。

#### P0-2　`importSave` 校验可被畸形存档击穿（崩溃而非拒绝）🔴 ✅已修复

**位置**：`scripts/qingshi/engine.lua:1355-1462`

该函数有约 100 行防御性校验，但**若干字段在校验前就被 `pairs`/`#` 消费**，畸形数据直接抛异常而非返回 `false`。对 27 个字段做类型 fuzz 的结果：

```
attrs=number   => THREW: engine.lua:1362: attempt to get length of a number value
attrs=bool     => THREW: engine.lua:1362: attempt to get length of a boolean value
once=number    => THREW: engine.lua:51:  bad argument #1 to 'for iterator'
once=string    => THREW: engine.lua:51:  bad argument #1 to 'for iterator'
introNotes=num => THREW: engine.lua:57:  attempt to get length of a number value
snapshot=number=> THREW: engine.lua:1361: attempt to index a number value
diffKey=bogus  => THREW: engine.lua:1370: attempt to index a nil value (field 'diff')
```

对照可见 `dev`/`zg`/`peak`/`keyChoices`/`age`/`bt`/`chapterIdx` 等字段都正确 `return false`，**唯独上述 6 处是抛异常**。

**根因**：
- `engine.lua:1361` — `J(s)` 对 number/boolean 返回 true，未做 `type(s) == 'table'` 判定
- `engine.lua:1362` — `#s.attrs` 在 `type` 校验前执行
- `engine.lua:1364` — `pairs(s.attrs)` 同上
- `engine.lua:1363/1414` — `_readOnce(s)` 内 `shallow(s.once)`（`:51`）与 `copyArr(s.introNotes)`（`:57`）无前置类型守卫
- `engine.lua:1370` — `self.diff` 在 `NewGame:78` 对未知 `diffKey` 取值为 `nil`，此处直接索引

**触发路径真实存在**：`home.lua:41` 的 `loadSaveInfo` 从磁盘读档，文件被截断或手改即命中。`enterSave`（`home.lua:48-57`）未包 `pcall`，异常会冒泡到 UI 事件循环。

**修复**：

```lua
-- 置于 engine.lua:1360 之后
if type(s) ~= 'table' or type(s.attrs) ~= 'table' then return false end
if s.once ~= nil and type(s.once) ~= 'table' then return false end
if s.introNotes ~= nil and type(s.introNotes) ~= 'table' then return false end
```

并为未知难度键兜底（`engine.lua:78`）：

```lua
self.diff = data.DIFFICULTY[diffKey] or data.DIFFICULTY.normal
```

#### P1-6　`applyEff` 用 `pairs` 遍历属性，结算面板条目顺序不定 🟠 ✅已修复

> **初版描述有误，此处更正**：原文写「顺序随机」，实测后应表述为「**任意（哈希）序**」。`pairs` 对**同一个表**的遍历顺序是稳定的（`distinct=1`），但该顺序由哈希决定，**既不同于 JS 的插入序，也因表而异**——因此游戏内不同选项/事件会呈现出彼此不一致的属性排列，且与 JS 参考实现对不上。并非「每次运行都变」。

**位置**：`scripts/qingshi/engine.lua:963`（`eff.attrs`）、`:979`（`setAttrs`）、`:990`（`condAttrs`）

JS 侧 `Object.keys` 保证插入序，Lua `pairs` 不保证。实测对比：

```
lua = zhengji,tupo,moulue,junxin,caifu,biancai,quanshi,weiji,shengwang,wuli,caixue   ← 修复前
js  = tupo,wuli,caixue,moulue,biancai,caifu,shengwang,quanshi,junxin,weiji          ← JS 基准
```

`changes` 直接喂给 `game.lua:171` 的结算浮层逐条渲染，**玩家看到的属性变动条目排列是任意的**。

需说明：`p2-replay` 100/100 全绿**掩盖了此问题**——`changes` 是展示字段不进快照，`engine.lua:9` 的契约 6 也明确写了「乱序只许落在 reason/changes 等不进快照的展示字段」。**作者知情并有意接受**，但 UI 已实际使用该字段，影响真实存在。

**修复**：新增 `orderedAttrKeys()`，按 `ATTRS` 声明序（与 UI 侧栏展示序一致）产出键序列。5 个剧本的 `ATTRS` 声明序完全一致，且实测 `eff.attrs` 的键域**严格是 `ATTRS` 的子集**（`eff_outside = none`），故按声明序遍历无损。未登记的键按字典序追加在后——**不静默丢弃**，将来数据新增属性也不会悄悄漏算。

### D.3 P2-9 `cardDesc` 完整移植

移植中踩到一个真实的坑：**Lua 模式按字节匹配，不能用 `[^（）]` / `[≥>]` 定位中文括号与全角符号**。`（`（EF BC 88）、`）`（EF BC 89）、`≥`（E2 89 A5）都是 3 字节，写进字符类等于逐字节排除 EF/BC/88/89/E2/89/A5——而这些字节在中文里极常见（如全角逗号 `，` = EF BC 8C），会把正常文案整段排除掉。

改用 `string.find(..., true)`（plain）切括号 + `%d`/`%s`（ASCII）匹配数字，字节安全。
