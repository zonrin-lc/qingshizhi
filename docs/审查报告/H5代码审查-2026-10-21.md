## 零、结论摘要

工程骨架是健康的:分层清楚(存档只出纯数据 / UI 只管存取 / 引擎只管规则),降级策略完备(容器探测、频控窗口、15 秒超时、备份键),注释密度与设计取舍记录远高于一般项目。

但这次审查挖出一条贯穿性主线:**「验证绿灯」与「代码真实状态」之间存在多处缺口**——三处门禁在空转(§一),八条数据正确性缺陷可导致玩家进度静默丢失或被云端旧包覆盖(§二),十数条 UI 层的收尾/泄漏问题(§三),以及一批恒真断言让测试「看起来在管事」(§五)。

按「玩家损失」排序,最该先动的是 §二 的 1–4 条(云存档元数据与临时文件)、§一 的 1–2 条(门禁),以及 §四 的 1 条(封存 Lua 数据分叉 —— 这条是本项目自己上周的提交漏了第四份产物)。

## 一、门禁空转:三处「绿灯是假的」

### 1.1 `p2-replay` 的对拍基线比引擎旧 21 小时 —— 已复核

- **位置**:`prot/lua-data/golden.json`(2026-10-20 02:25)vs `prot/engine.js`(2026-10-21 01:11);`prot/p2-replay.js:9` 读 golden
- **现象**:引擎改过之后 golden 没重算,`node p2-replay.js` 仍打印 `pass=100 fail=0` —— 它验的是「旧 JS vs Lua」,当前引擎从未与 Lua 对拍过
- **影响**:`npm run verify:replay` 的绿灯不能当作 JS/Lua 一致的证据;引擎最近的所有改动(含 10-21 的险招失败即事件终结)都没被 Lua 侧覆盖
- **建议**:把「golden 新鲜度」做成硬门禁——`p1-golden.js` 之后 `git diff --exit-code prot/lua-data/golden.json`,或让 `p2-replay` 先重算再比

### 1.2 封存 Lua 版的李斯数据仍是旧文案(上周提交漏了第四份产物)—— 已复核

- **位置**:`scripts/qingshi/data/lisi.lua` 的 `ACTIONS[9]`(ACT-7)
- **现象**:`rg -c "乡绅联姻" scripts/qingshi/data/lisi.lua` = 1,`rg -c "结交富室"` = 0;而 `prot/lua-data/lisi.json`、`prot/lua/data/lisi.lua`、`prot/game-data.js` 都已是新文案「结交富室 / 倾身结纳,倚为奥援」
- **根因**:提交 `44975ef` 只更新了三份产物,漏了 `scripts/qingshi/data/` 下的第四份;而 `scripts/FROZEN.md:31-34` 明写「两边必须逐字节一致(p1-verify 会校验)」
- **佐证**:`p1-verify` 只比 `prot/lua-data/*.json` ↔ `prot/lua/data/*.lua`,**从不看 `scripts/` 下那份**;两目录连换行符都不同(CRLF vs LF),「逐字节一致」在现状下并不成立
- **影响**:封存 Lua 版仍显示带「（嫁）（聘礼）」性别分支的旧卡(正是那次改动要删的);`p2-replay` 消费的就是这份 stale 数据
- **建议**:补一条 `scripts/qingshi/data/*.lua` ↔ `prot/lua-data/*.json` 的等价校验并纳入 `verify:data`

### 1.3 数据生成链方向与文档相反,跑一次就静默回滚改动 —— 已复核

- **位置**:`prot/dump-lua-data.js:71-97`;`scripts/FROZEN.md:27-34`
- **现象**:dump-lua-data 是**从 `scripts/qingshi/data/*.lua` 反向生成 `prot/lua-data/*.json`**(再由 p1-convert / sync-data-js 生成 Lua 与 JS);文档写的却是「改 prot/*-data.js → p1-golden → p1-convert」
- **影响**:谁跑一次 `node dump-lua-data.js lisi`,JSON 就退回旧 ACT-7 文案,而 `p1-verify` 仍绿(两侧一起旧);`align()` 只回填旧 JSON 里的 `null` 键,Lua 侧误删非空键时 JSON 同步消失且无人报警
- **建议**:确定单一真源(建议 `prot/lua-data/*.json`),把 dump-lua-data 改成「校验」而非「生成」,align 改成缺键即报错

## 二、高危:玩家进度会丢或会被云端覆盖

### 2.1 上传在飞时新增的存档,脏标记被回滚成「永不上云」 —— 已复核

- **位置**:`h5/src/game/tapcloud.ts:205`(读 meta 快照)、`:233`(`writeMeta({ ...meta, lastUpload: Date.now() })`)
- **现象**:上传要经历 3 次网络往返;期间玩家存了档,`scheduleUpload` 把 `lastChange` 推到 T2;上传结束却用 **T1 的旧快照** 把 `lastChange` 一起写回 → 变回 T1
- **影响**:`pending` 变 false、`m.lastChange > m.lastUpload` 不成立 → **这次存档再也不会上云**,设置页却显示「已同步」
- **建议**:写回时只更新 `lastUpload`(现读现用),或 `Math.max(meta.lastChange, 当前值)`

### 2.2 上传与下载共用同一个临时文件路径,互不排斥 —— 已复核

- **位置**:`tapcloud.ts:168-169`(`bundlePath` 固定 `qingshi_saves.json`)、`:215`(上传 writeFile)、`:273`(下载 targetFilePath)
- **现象**:上传把本地整包写进该文件再交给 `updateArchive`;下载 `getArchiveData` 又把云端内容落到同一路径;`applyCloudBundle` 不设 `syncing`,`runUpload` 只防同类并发
- **影响**:启动对账的下载未结束时,写档触发 `scheduleUpload` → 1.5s 后上传开跑 → 下载把**旧云端内容**写回该文件 → 上传归档了旧内容(新档被云端回滚),本地又被下载覆盖
- **佐证**:测试 mock(`tests/tapcloud.cjs:80-87`)证实两者写同一个 `files[path]`
- **建议**:上传/下载各用独立临时文件名,或给二者共用一把互斥锁

### 2.3 脏标记只在「已登录」时才写 → 登录一失败,云端旧包恒胜 —— 已复核

- **位置**:`tapcloud.ts:248`(`if (!isTapEnv() || !online) return;`)、`:307`(对账条件 `cloudAt > meta.lastChange`)
- **现象**:离线/登录失败时 `meta.lastChange` 恒为 0,而对账拿云端时间戳与 0 比 → 云端(哪怕是旧包)恒胜
- **影响**:**整包覆盖本地,本机进度静默丢失**;备份键 `qingshi.cloudbackup.v1` 只有测试读过,产品里没有任何恢复入口;`:329-330` 的 `inited = true` 早置还让一次登录失败永久关闭本会话的云同步(无重试)
- **建议**:脏标记无条件落盘(与 online 解耦);对账改用「本地是否存在未上传改动」而非单纯时间戳比较

### 2.4 整包导入忽略写入失败,却照样把 meta 对齐云端 —— 已复核

- **位置**:`h5/src/game/saves.ts:343-349`(`importSavesBundle` 丢弃 `writeAutos`/`writeStash` 返回值)、`tapcloud.ts:284-293`
- **现象**:两次 `setItem` 分属两个键,配额不足时只成功一半 → **半新半旧的存储**;`applyCloudBundle` 仍返回 true,UI 弹「已用云端存档覆盖本地」,随后把 `lastChange/lastUpload` 对齐云端 → 分叉的那一半被标记「已同步」,永不重传
- **附带**:`tapcloud.ts:279` 只校验 `bundle.saves` 存在,云端包若是 `saves:{}` 就会把本地 autos + stash 清空
- **建议**:先写成功再落 meta,失败回滚并抛错;导入前校验 `v` 与 autos/stash 结构

### 2.5 存档桶没有任何形状校验,一个非数组的桶让两条链同时抛 —— 已复核

- **位置**:`saves.ts:89-98`(`readAutos`/`readStash` 原样放行)、`:161-169`(`listAutoEntries` / `saveAuto` 直接 `.map`/`.push`)
- **现象**:云端整包里 `autos.lisi` 不是数组(老版本包 / 手改 localStorage)→ 存档页整页渲染失败;`saveAuto` 的 `list.push` 同样抛 → 对局页点「返回」时异常中断,**玩家退不出这一局**(`main.ts:179/197` 无 try)
- **建议**:`importSavesBundle` 逐桶逐条深校验(`Array.isArray(bucket)` + `slot.at/payload` 类型),非法整桶丢弃;`listAutoEntries/saveAuto` 入口再防御一次

### 2.6 `thaw()` 清掉手牌却不重发,引擎拒绝一次操作即死局 —— 已复核

- **位置**:`h5/src/game/session.ts:1834-1838`
- **现象**:`thaw` 只 `clearOpts()` 再补一行提示,没有任何重发牌逻辑
- **影响**:`playCard/choose/chooseCardOption` 一旦返回 null(相位错位或卡面判定与引擎不一致),界面上再无任何可点牌,只能回溯或退出;硬核难度无回溯即本局报废
- **建议**:thaw 后按引擎当前状态重发牌(`renderRound()`),或保留原卡只提示不销毁

### 2.7 事件自环:同一选项可无限次重复结算 —— 已复核(实扫)

- **位置**:实扫五本剧本,命中 5 处 —— `hanxin` 2-4、`jingke` 2-2 / 3-1、`lisi` 1-4 / 3-2;`prot/engine.js:985` 写入的 `passedEvents` 全项目无人读取
- **现象**:`jingke` 第 3 章 3-1 选项 2「劝太子丹亲杀之」`to: "3-1"`、无 flag/req 守卫;`lisi` 3-2 选项 1 的 `to` 数组含 `{if:{flag:'guangjiaoyou'},to:"3-2"}`(flag 永不清除)
- **影响**:连续重选可反复应用「君心-5/名声-3/危机+3/偏离+3」,把偏离度推满 100(逆天段)
- **建议**:引擎侧按 (章, eventId, 选项下标) 记录已用并锁;数据侧给自环选项补 `flags` + `notflag` 守卫

### 2.8 剧情难度的「无限回溯」被 H5 私自砍成每章 1 次 —— 已复核

- **位置**:`h5/src/game/session.ts:238`(`const locked = !can || g.backtracksThisChapter > 0;`)、`:252`、`:254`;引擎 `prot/engine.js:1330-1337`
- **现象**:引擎 `canBacktrack` 只在 `diff.backtrack > 0` 时计数封顶,`backtrack = -1`(剧情难度,难度表写着「无限回溯」)不设限;H5 额外加了一刀 `backtracksThisChapter > 0`
- **影响**:剧情难度实际只剩 1 次/章,`coef×0.98` 的递减机制形同虚设;而同文件 `:254` 的确认框按 `quota > 0 ? … : null` 渲染成「本章可无限次回溯」—— **界面承诺与逻辑相反**;存档页 `savepage.ts:198` 还显示「可回溯 0 次」(`saves.ts:177,275` 用 `max(0, -1-n)` 算成 0)
- **建议**:回溯判定改为 `g.diff.backtrack > 0 ? g.backtracksThisChapter >= g.diff.backtrack : false`;`-1` 用哨兵值表示「无限」,展示层再翻译

## 三、中危

> 以下除标注外均为「已复核」;「待复现」项是审查员提出、逻辑自洽但我没有跑出复现步骤。

### 3.1 音频错误路径:一次 404 静音整局 —— 已复核

- **位置**:`h5/src/game/audio.ts:187-191`(error 监听里 `this.failed = true; this.stop();`)、`:118`(`stop()` 里 `this.el.currentTime = 0`)
- **现象**:资源加载失败时 `readyState === HAVE_NOTHING`,按规范给 `currentTime` 赋值会抛 `InvalidStateError` → 异常逃出事件监听器,`current`/`rotateKey`/`pausedByHidden` 的清理被跳过;`failed` 标志是全局熔断且**永不复位**(`:89/:93/:106` 三处早退)
- **影响**:某个剧本缺曲或 404 → 菜单 idle 曲从此整局静音,且错误路径没有任何日志
- **建议**:`currentTime` 包 try/catch(同仓 `sfx.ts:66-70` 已规避同一坑);`failed` 改成按曲目记录、`start()` 成功后复位

### 3.2 设置值不做类型/区间校验,坏值能把音量设成 NaN —— 已复核

- **位置**:`h5/src/game/settings.ts:70-81`(`o.musicGain ?? DEFAULTS.musicGain` 只挡 null/undefined)
- **影响**:`"abc"` 原样通过 → `audio.ts:126` 的 `Math.min(1,"abc")` = NaN → `el.volume = NaN` 按 WebIDL 抛 TypeError;`segDelay` 可被改成 1e9 让叙事看起来卡死;`updateSettings` 以坏值为基底,坏值会被永久写回
- **建议**:逐字段 `Number.isFinite` + 夹取,非法落回默认值

### 3.3 删除存档的确认浮层删除成功后不关闭 —— 已复核

- **位置**:`h5/src/ui/savepage.ts:339`(`btn('删 除', { variant: 'primary', onClick: onYes })`,没有 `ov.remove()`)
- **佐证**:同仓 `settings.ts:237`、`main.ts:196` 的同类浮层都写了 `ov.remove()`,只有存档页这一处漏
- **影响**:档已删、列表已在蒙版背后刷新,但「删除存档？」蒙版仍盖满整页,「读 取/删 除」全被挡住,玩家以为删除失败或界面卡住
- **建议**:`onClick: () => { ov.remove(); onYes(); }`

### 3.4 设置页没有 destroy,`onStatus` 订阅泄漏 —— 已复核

- **位置**:`h5/src/ui/settings.ts:187-191`;`h5/src/main.ts:139-140`(`hidePages` 用 `querySelector('.settings')?.remove()` 直接摘 DOM)
- **影响**:每次进设置页都新增一个订阅,回调闭包持有已脱离文档的整棵子树;自退订只在「下次状态事件到来且 root 已断开」时发生 —— 没有状态事件就永久泄漏
- **建议**:给设置页加 `destroy()`,`hidePages()` 统一调用(同 menu/select/gallery)

### 3.5 外壳补丁每次重建右栏,「旧值保持到落定 + 雷达补间」被绕过 —— 已复核(效果需目视确认)

- **位置**:`h5/src/main.ts:419-423`(`session.renderTop` 被包一层,每次都 `renderSide(shell.side, session.sideContent())`)、`h5/src/game/session.ts:799-843`(pending 机制)、`:886/:905`(守卫 `vEl.textContent !== oldShown` 就 return)
- **机制**:右栏被整体重画成当前值 → 稍后 `applySideDelta` 触发时守卫命中 → 补间不执行,`pending` 也不 `delete`(脏值长期累积)
- **建议**:`sideContent()` 接受并透传 pending 覆盖值,或在有 pending 时跳过右栏重建

### 3.6 对账拿云端「上传时刻」比本地「变动时刻」,语义不对 —— 已复核

- **位置**:`tapcloud.ts:289`(`found.modifiedTime * 1000`),而 `:212/:224` 明明把本地变动时刻写进了包的 `at` 与 `extra`
- **影响**:上传必然发生在变动之后 → 每次成功上传后的启动都满足 `cloudAt > lastChange` → **每次启动白白下载一次并整包重写本地 autos/stash**(还刷新一次备份);多设备场景更会用整包盖掉本机未上传的进度
- **建议**:解析 `extra.at`(或包里的 `at`)与本地 `lastChange` 比

### 3.7 调度器只在成功时补排,throttled/busy/failed 之后改动被搁置 —— 已复核

- **位置**:`tapcloud.ts:254-260`(`if (ok && m.lastChange > m.lastUpload) scheduleUpload();`)
- **影响**:`:176-179` 注释承诺「失败不丢数据,下个窗口调度器还会再来」,但 `throttled` / `busy` / `failed` 都不满足 `ok` → pending 一直挂着没人再推,直到下一次写档或下次启动
- **建议**:失败分支也按 `uploadInterval()` 重排一次

### 3.8 退出前的云档 flush 实际是空操作 —— 已复核

- **位置**:`tapcloud.ts:409-424`(`void uploadNow()` 不等待就接着关页;`uploadNow` 内部先过 60s 频控窗口)
- **影响**:进程多半在上传落地前就被掐掉;且窗口内直接返回 `throttled` → 退出时几乎永远传不上去
- **建议**:退出时先 `await` 上传(带 2–3s 上限)再关,或去掉这段假装 flush 的代码并在 UI 上如实说明「本次改动未上云」

### 3.9 朗读:每条切片挂两个 `{once:true}` 监听,只有一个被消费 —— 待复现

- **位置**:`h5/src/game/voice.ts:161-162`、`:108-113`
- **风险**:陈旧回调会写共享状态 `settleCurrent`(那根防「pump 永久卡在 await」的救命稻草),一旦被置空,`stop()`/回前台续播就再也结算不了当前句,`pump` 死等、之后所有朗读被静默丢弃
- **建议**:只在元素上挂一对常驻监听,用「当前句 token/URL」判断事件归属

### 3.10 语音/音效的 `{once:true}` 监听与 `settleCurrent` 竞态 —— 待复现(与 3.9 同源)

### 3.11 设置值/图鉴持久化没有 schema 版本,图鉴写回点缺失 —— 已复核

- **位置**:`h5/src/game/collection.ts:85-90`(`saveCollection` 全仓无调用点)、`:44/:86`(`loadCollection` 因 `gloss/ach` 非数组就整体返回 null → 一次畸形存储清空该剧本的结局记录)

### 3.12 两套 toast 实现互相劫持,提示会被吞 —— 已复核

- **位置**:`h5/src/ui/kit.ts:107-122` 与 `h5/src/main.ts:236-247` 共用 `.toast` 类;`main.ts` 的 `shell.stage.querySelector('.toast')` 会命中 kit 挂在页面根里的那个节点
